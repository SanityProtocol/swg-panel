# swgPanel на NixOS

Запускайте панель, узел или и то и другое на NixOS — декларативно. Поддерживаются два способа
доставки, и ни один из них не является ступенькой к другому: **контейнерный вариант**, который
запускает публикуемые нами образы, и **нативный вариант**, который запускает эти же программы из
вашего Nix store поверх ядерного датапата. Есть и `nix/adopt.sh` — перенос уже работающей машины на
любой из двух вариантов, без перевыпуска хотя бы одного ключа.

Страница выстроена по задачам: начните сверху и закончите работающей установкой.

⚠️ **Не запускайте `bootstrap.sh` на NixOS.** Он откажется — как и `install-host.sh`,
`install-node.sh`, `install-docker.sh`, `update.sh` и `convert.sh`. Их пришлось этому научить,
потому что отказ был неочевиден: `/` доступен на запись, а `nixos-rebuild` никогда не трогает
`/opt`, поэтому `mkdir -p /opt/… && cp` **срабатывает**, и установка спотыкается лишь позже — на
`PATH` или `apt-get`, оставляя полуустановку, которой ваша конфигурация не видит. `--dry-run`
по-прежнему работает: так можно посмотреть, что установка на голое железо *записала бы* на машине,
с которой вы переезжаете.

## Что нужно до начала

- Машина с NixOS, где вы можете выполнить `nixos-rebuild switch` — флейки это документированный
  путь, а `default.nix` даёт пользователям каналов те же выходы и без них.
- **Файл с секретами на машине, вне Nix store.** Каждый токен и пароль лежит в файле; значение
  опции попадает в store, доступный на чтение всем. Путь из менеджера секретов тоже подойдёт
  (`config.sops.secrets.swg-panel.path`, agenix, …).
- Для панели: домен и что-нибудь, что терминирует TLS — `security.acme` плюс обратный прокси, либо
  сама панель через `useACMEHost`.
- Для узла: публичный IP, на который будут подключаться клиенты, и токен узла, выпущенный в
  экране **Nodes** панели (показывается один раз).

## Установка

### Шаг 1 — флейки

**Чтобы это установить, включать флейки не нужно.** `nixos-rebuild --flake` включает их для
собственных вызовов `nix` — nixos-rebuild сам передаёт `--extra-experimental-features "nix-command
flakes"`, — поэтому любой `nixos-rebuild` из этого руководства работает на стоковой машине с
выключенными флейками.

Что действительно их требует — это голая команда **`nix`**: `nix build`, `nix flake check`,
`nix flake update`. Одну из них запускает кнопка Update панели, и их же используют проверочные
команды в шаге 2. Поэтому добавьте строку сейчас, а применит её первая пересборка, в шаге 9:

```bash
sudo nano /etc/nixos/configuration.nix
```

Внутрь внешних `{ … }`, где угодно среди остальных настроек:

```nix
  nix.settings.experimental-features = [ "nix-command" "flakes" ];
```

Сохраните и выйдите из nano: **Ctrl+O, Enter, Ctrl+X**. Пока шаг 9 её не применил, голой команде
`nix` нужен явный флаг:

```bash
nix --extra-experimental-features 'nix-command flakes' flake metadata /etc/nixos
```

⚠️ **Не пытайтесь применить её обычным `sudo nixos-rebuild switch`.** Без `--flake` этой команде
нужна запись `nixos-config` в `NIX_PATH`, а у машины, которая уже управляется флейком — или просто
развёрнута без каналов, — её нет. Она падает с
`error: file 'nixos-config' was not found in the Nix search path`, не успев ничего изменить.

### Шаг 2 — создайте флейк

Что в нём будет, определяют две вещи: **где лежит ваша конфигурация** (`/etc/nixos`, если вы её не
переносили) и **имя хоста** — флейк называет свою конфигурацию по имени машины.

```bash
hostname          # например, "myhost" — используйте то, что напечатает, во всех командах ниже
nixos-version     # например, "25.11.2026…" — канал, на котором эта машина СЕЙЧАС
```

⚠️ **Прикрепите nixpkgs к тому каналу, который только что напечатал `nixos-version`**, а не к
самому свежему. Вход `nixpkgs` флейка *и есть* набор пакетов вашей системы, поэтому более высокий
канал здесь обновит всю ОС на следующей пересборке — изменение куда крупнее, чем установка этой
панели, и не то, которое стоит сделать случайно. `25.11` ниже — пример; поставьте свой.

Создайте файл:

```bash
sudo nano /etc/nixos/flake.nix
```

Вставьте это, заменив **`myhost`** на то, что напечатал `hostname`:

```nix
{
  inputs.nixpkgs.url = "github:NixOS/nixpkgs/nixos-25.11";   # ← ВАШ канал, из `nixos-version`
  inputs.swg-panel.url = "github:SanityProtocol/swg-panel";

  outputs = { self, nixpkgs, swg-panel, ... }: {
    nixosConfigurations.myhost = nixpkgs.lib.nixosSystem {    # ← ВАШЕ имя хоста
      system = "x86_64-linux";                 # aarch64-linux на ARM — подскажет `uname -m`
      modules = [
        ./configuration.nix
        swg-panel.nixosModules.default         # панель + узел; .swg-panel или .swg-node по отдельности
      ];
    };
  };
}
```

Сохраните (**Ctrl+O, Enter, Ctrl+X**) и проверьте, что он вычисляется, прежде чем что-то собирать:

```bash
sudo nixos-rebuild build --flake /etc/nixos#myhost
```

Тихое завершение или строка, оканчивающаяся на `/nix/store/…-nixos-system-myhost-…`, означает, что
всё в порядке. Пока ничего не меняется — `build` только собирает. Если он падает с **`error: Path
'flake.nix' in the repository "/etc/nixos" is not tracked by Git.`**, значит ваш `/etc/nixos` — это
git-репозиторий, а git ничего не знает о новом файле:

```bash
sudo git -C /etc/nixos add flake.nix
```

Nix читает из git-каталога только *отслеживаемые* файлы, поэтому неотслеживаемый `flake.nix` для
него невидим.

Трогать `/etc/nixos/configuration.nix` снова не нужно — флейк подтягивает его строкой
`./configuration.nix`, так что всё, что уже есть на машине, продолжает работать.

**Совсем без флейков?** Пакет доступен и по-старому, хотя примеры модулей ниже рассчитаны на флейк:

```nix
(import (fetchTarball "https://github.com/SanityProtocol/swg-panel/archive/main.tar.gz"))
  .packages.x86_64-linux.default
```

**Хотите сначала посмотреть, ничего не решая?** Эти команды не трогают машину:

```bash
nix build github:SanityProtocol/swg-panel          # просто собирает пакет
nix flake check github:SanityProtocol/swg-panel    # ⚠️ собирает две виртуалки NixOS — минуты, не секунды
```

Чтобы собирать против **вашего** nixpkgs, а не нашего, добавьте оверлей в `configuration.nix`:

```nix
nixpkgs.overlays = [ inputs.swg-panel.overlays.default ];   # → pkgs.swg-panel
```

### Шаг 3 — выберите способ доставки

|  | `container` (по умолчанию) | `native` |
|---|---|---|
| что запускается | публикуемые нами образы | наши программы из вашего store |
| датапат | модуль ядра, **если он есть на хосте** (см. [шаг 7](#шаг-7--необязательно-дать-контейнерному-узлу-ядерный-датапат)), иначе userspace | модуль ядра, устанавливаемый этим модулем |
| подверженность проблемам с модулем ядра | **нет** | модуль, который не соберётся, **обрушит ваш `nixos-rebuild`** |
| в вашем замыкании и откатах | дайджест образа | всё |
| turn / WDTT / csqtt | соседние контейнеры + управляемые подпроцессы | юниты хоста, в проверенном каталоге юнитов |
| перезагрузка после первого switch | нет | да, один раз, ради модуля ядра |

Грубый ориентир: берите **native** ради пропускной способности и замыкания, в котором есть всё;
берите **container**, чтобы дерево ядра хоста вообще не участвовало. Перед тем как остановиться на
нативном варианте, прочитайте [Где заканчивается поддержка](#где-заканчивается-поддержка) — это
единственная граница, которую стоит знать заранее.

⚠️ **В контейнерном варианте ставьте `backend = "podman"`.** По умолчанию там `docker`, а nixpkgs
помечает пакет `docker` как insecure — поэтому машина с `backend = "docker"` откажется вычисляться
на стоковом канале, пока вы не поднимете nixpkgs или не добавите
`nixpkgs.config.permittedInsecurePackages`. У podman такого флага нет, а образ он запускает тот же.
Во всех контейнерных примерах ниже это прописано.

### Шаг 4 — положите секреты на машину

Записывайте только то, что нужно этой машине: панели нужен пароль, узлу — токен, мастеру — и то и
другое.

⚠️ **Токен узла берётся у уже работающей панели.** Если это ваша первая машина, установите сейчас
**панель** (строки про узел пропустите), затем выпустите токен в её экране **Nodes** и вернитесь
сюда. Единственное исключение — **мастер**, где вы генерируете токен сами до запуска обеих служб;
ровно ради этого и существует `localNode`, а как именно — показано в его блоке в шаге 5.

```bash
sudo install -d -m 0700 /etc/swg-secrets

# Панель: НАЧАЛЬНЫЙ пароль входа.
printf 'PANEL_PASSWORD=%s\n' 'choose-something-long' | sudo tee /etc/swg-secrets/panel.env >/dev/null

# Узел, контейнерный вариант: токен из экрана Nodes панели.
printf 'NODE_TOKEN=%s\n' 'paste-the-token' | sudo tee /etc/swg-secrets/node.env >/dev/null

# Узел, нативный вариант: СЫРОЙ токен, без префикса KEY=.
printf '%s' 'paste-the-token' | sudo tee /etc/swg-secrets/node-token >/dev/null

sudo chmod 0600 /etc/swg-secrets/*
```

`PANEL_PASSWORD` задаёт **начальный** вход и дальше игнорируется — файлом аутентификации владеет
сама панель, а пароль меняется в интерфейсе. Переустанавливать его при каждой загрузке значило бы
тихо отменять эту смену, поэтому модуль записывает пароль только тогда, когда входа нет вовсе.

Два написания токена не взаимозаменяемы. `tokenFile` несёт сырой токен и работает **только в
нативном** варианте (он читается через `LoadCredential` systemd); контейнерный вариант читает
`NODE_TOKEN=…` из `environmentFile`, потому что учётные данные хоста не пересекают границу
контейнера.

### Шаг 5 — опишите, что запускает эта машина

Всё дальнейшее идёт в **`/etc/nixos/configuration.nix`**, внутрь внешних `{ … }`, рядом с уже
имеющимися настройками:

```bash
sudo nano /etc/nixos/configuration.nix
```

Выберите один из трёх блоков ниже и вставьте его. Блоки написаны как целые файлы — если вы
вставляете в существующий `configuration.nix`, берите только строки `services.swg-*` (и
`security.acme`, `services.nginx`, …), а его собственные внешние скобки и заголовок
`{ config, pkgs, ... }:` оставьте как есть. Сохраните **Ctrl+O, Enter, Ctrl+X**; применит это шаг 9.

Ту же последовательность — файл с токеном → `flake.nix` → `nixos-rebuild` — печатает экран
**Nodes** панели, уже подставив ваши значения, если вам удобнее скопировать оттуда.

#### Панель

```nix
{
  services.swg-panel = {
    enable = true;
    backend = "podman";                                  # delivery по умолчанию "container"
    domain = "panel.example.org";
    environmentFile = "/etc/swg-secrets/panel.env";      # должен определять PANEL_PASSWORD=

    # Где публикуются ссылки подписок. Укажите это, иначе выдать их не получится — см. ниже.
    sub.publicUrl = "https://panel.example.org";
  };

  # По умолчанию панель слушает 127.0.0.1:8443. Терминируйте TLS перед ней.
  security.acme = {
    acceptTerms = true;                                  # обязательно, иначе сертификат не выпустится
    defaults.email = "you@example.org";
  };
  services.nginx.virtualHosts."panel.example.org" = {
    enableACME = true; forceSSL = true;
    locations."/".proxyPass = "http://127.0.0.1:8443";
  };
}
```

Если вы предпочитаете, чтобы TLS терминировала сама панель и обратного прокси не было, поставьте
`useACMEHost = "panel.example.org"` и `host = "0.0.0.0"`: она прочитает сертификат, которым уже
управляет `security.acme`, войдёт в его группу и будет перезагружаться при продлении.

⚠️ **`host` по умолчанию `127.0.0.1`.** Это верно за локальным обратным прокси и неверно во всех
остальных случаях: панели, к которой обращаются напрямую или проксируют с другой машины, нужен
`host = "0.0.0.0"`, иначе к ней невозможно подключиться.

⚠️ **Если не задан ни `sub.domain`, ни `sub.basePath`, ни `sub.publicUrl`, база подписок не
записывается вовсе, и ссылки подписок выдать нельзя.** Это сделано намеренно: единственный адрес,
который модуль мог бы вывести сам, — это адрес самой панели, а ссылка подписки, открывающая панель,
хуже, чем ссылка, которой явно ещё нет. Если swgSub живёт на том же имени, но на другом порту,
скажите это явно — угадывать URL, ведущий на панель, модуль отказывается.

Страница подписок (**swgSub**) идёт вместе с панелью в обоих вариантах и ставится **инертной**: вся
поверхность отдаёт 404, пока вы не включите её в Settings → Subscriptions.

#### Узел

**Контейнерный вариант:**

```nix
{
  services.swg-node = {
    enable = true;
    backend = "podman";
    panelUrl = "https://panel.example.org:8443";
    endpoint = "203.0.113.10";                           # публичный IP, на который идут КЛИЕНТЫ
    environmentFile = "/etc/swg-secrets/node.env";       # определяет NODE_TOKEN=
  };
}
```

**Нативный вариант:**

```nix
{
  services.swg-node = {
    enable = true;
    delivery = "native";
    panelUrl = "https://panel.example.org:8443";
    endpoint = "203.0.113.10";
    tokenFile = "/etc/swg-secrets/node-token";           # сырой токен
  };
}
```

Первый нативный switch устанавливает модуль ядра AmneziaWG, поэтому после него **один раз
перезагрузитесь** — до этого `awg-quick` работает на userspace-датапате. Модуль скажет об этом,
когда это важно, и промолчит, когда нет.

Порты всех интерфейсов в обоих вариантах оказываются на хосте (netns хоста), поэтому публиковать
нечего: и тот, что вы настроили, и все, которые панель выберет позже, уже там.

#### Мастер — панель и узел на одной машине

Другие способы установки предлагают то же самое; здесь это `localNode`, и убирает он лишний круг.
Без него вы поднимаете панель, выпускаете токен в экране Nodes, кладёте его в файл секретов и
пересобираете ещё раз. Токен вы генерируете сами; в Nix store не попадает ничего. Отдайте один и
тот же токен обоим модулям:

```bash
tok=$(head -c 32 /dev/urandom | od -An -tx1 | tr -d ' \n')   # 64 hex-символа, только coreutils
printf '%s' "$tok" | sudo tee /etc/swg-secrets/node-token >/dev/null
printf 'NODE_TOKEN=%s\n' "$tok" | sudo tee /etc/swg-secrets/node.env >/dev/null
sudo chmod 0600 /etc/swg-secrets/node-token /etc/swg-secrets/node.env
```

```nix
{
  services.swg-panel = {
    enable = true;
    backend = "podman";
    domain = "panel.example.org";
    environmentFile = "/etc/swg-secrets/panel.env";
    sub.publicUrl = "https://panel.example.org";
    localNode = { enable = true; tokenFile = "/etc/swg-secrets/node-token"; };
  };

  services.swg-node = {
    enable = true;
    backend = "podman";
    endpoint = "203.0.113.10";                           # куда идут КЛИЕНТЫ
    panelUrl = "http://127.0.0.1:8088";                  # куда идёт ЭТОТ узел — см. ниже
    verifyPanelTls = false;
    environmentFile = "/etc/swg-secrets/node.env";       # тот же токен
  };
}
```

Панель хранит только хэш токена. Повторный запуск безопасен: запись, которая и так проходит
проверку, остаётся нетронутой, а запись с изменившимся токеном обновляется на месте, а не
дублируется.

⚠️ **Узел обращается к `http://127.0.0.1:<localPort>`, а не к публичному адресу.** Эта точка входа
существует ровно для этого, и смена публичного адреса её никогда не двигает — обращение к
публичному URL погнало бы собственный узел машины через ваш обратный прокси и обратно и сломалось бы
при следующей смене адреса. Она **по построению работает по обычному HTTP** (панель добавляет её без
сертификата), поэтому `verifyPanelTls = false` здесь на месте; модуль предупредит, если направить её
на `https://127.0.0.1`.

На **нативном** мастере поставьте `delivery = "native"` в обоих модулях.

⚠️ **Этот блок не создаёт никакого пути ВНУТРЬ.** Это только половина с регистрацией: `host`
по-прежнему `127.0.0.1`, и TLS никто не терминирует, поэтому панель доступна с самой машины и больше
ниоткуда. Добавьте половину с `security.acme` + `services.nginx` из [блока панели выше](#панель) или
`useACMEHost` + `host = "0.0.0.0"` — ровно так же, как для панели самой по себе. На половину с узлом
это не влияет: он обращается к loopback-точке, а не к публичному адресу.

### Шаг 6 — откройте UDP-порты

**Не пропускайте этот шаг.** NixOS по умолчанию фильтрует `INPUT`, а порты наших интерфейсов
приходят от **панели, во время работы**, тогда как `networking.firewall` вычисляется во время
**сборки**. Если ничего не сделать, созданный в панели интерфейс синхронизируется, отчитывается
здоровым, показывает свои пиры — и ни один клиент до него не достучится.

В `/etc/nixos/configuration.nix`:

```nix
services.swg-node.udpPortRanges = [ { from = 51820; to = 51899; } ];
```

Это открывает диапазон **и** сообщает узлу, что именно было объявлено, поэтому **панель поднимет
проблему на узле** в тот момент, когда интерфейс окажется за его пределами, вместо того чтобы
оставить вас разбираться по соединению, которое просто не устанавливается. Держите диапазон в
согласии с тем, что вы используете в интерфейсе. Оставите пустым — модуль скажет об этом на этапе
сборки; `networking.firewall.enable = false` заглушит и то и другое.

### Шаг 7 — необязательно: дать контейнерному узлу ядерный датапат

Контейнерный вариант намеренно **не** объявляет модуль ядра — ровно это и означает строка
«подверженность проблемам с модулем ядра: нет». Он использует модуль хоста, если тот есть, и
userspace-датапат `amneziawg-go`, если нет. Хотите на контейнерном узле более быстрый датапат —
объявите модуль сами.

В `/etc/nixos/configuration.nix`:

```nix
boot.extraModulePackages = [ config.boot.kernelPackages.amneziawg ];
boot.kernelModules = [ "amneziawg" ];
```

После первого switch один раз перезагрузитесь. `services.swg-node.kernelModule` этого **не** делает
— это опция нативного варианта, и в контейнерном она бездействует.

### Шаг 8 — необязательно: разрешить панели управлять turn-прокси

Управление turn монтирует в узел сокет среды контейнеров, а это root на этой машине, поэтому в
контейнерном варианте оно выключено по умолчанию. На podman ему нужны ещё docker-совместимый CLI и
rootful-сокет — модуль это проверяет, а не падает потом непонятным образом.

В `/etc/nixos/configuration.nix`:

```nix
services.swg-node.turnManage = true;

virtualisation.podman = {
  dockerCompat = true;          # демон вызывает `docker`
  dockerSocket.enable = true;   # …и управляет соседними контейнерами через rootful-сокет
};
```

**Нативный** узел управляет turn-прокси безусловно, и никакой сокет в этом не участвует.

Если на контейнерном узле вы запускаете ещё и серверы **csqtt**, добавьте `seccomp = "unconfined"` —
см. [csqtt нужен seccomp](#csqtt-в-контейнерном-варианте-нужен-seccomp).

### Шаг 9 — пересоберите и проверьте, что всё поднялось

Примените всё (`myhost` — то, что напечатал `hostname` в шаге 2):

```bash
sudo nixos-rebuild switch --flake /etc/nixos#myhost
```

Первый запуск скачивает изрядно и может занять несколько минут. Заканчивается он строкой
`Done. The new configuration is /nix/store/…`, перечислив по пути запущенные юниты —
`podman-swg-panel.service`, `podman-swg-node.service` и прочие.

**Если он упал, ничего не изменилось.** `nixos-rebuild` атомарен: машина продолжает работать ровно
на том, на чём работала, так что можно прочитать ошибку, поправить файл и запустить снова. Если
пересборка *удалась*, но стало хуже, шагните на поколение назад:

```bash
sudo nixos-rebuild switch --rollback
```

Теперь проверьте службы. В контейнерном варианте имена с `podman-*`, в нативном — обычные:

```bash
# Панель
systemctl status podman-swg-panel      # или swg-panel-server в нативном варианте
curl -s -o /dev/null -w '%{http_code}\n' http://127.0.0.1:8088/healthz        # 200 = поднялась
```

`/healthz` — это неаутентифицированная проба живости на выделенном loopback-порту панели
(`localPort`, по умолчанию 8088). Любой путь `/api/` отвечает 401, пока вы не вошли, и это тоже
здоровый ответ — но *неверный путь* отвечает 401 точно так же, поэтому как проверка он плох.

```bash
# Узел
journalctl -u podman-swg-node -n 20    # или swg-noded в нативном варианте
```

Вы ищете `syncing to https://… (interfaces: …, endpoint …)` и **отсутствие** строк `sync error`.
`Connection refused` здесь означает, что узел не достучался до `panelUrl` — проверьте адрес, а на
мастере проверьте, что это loopback-адрес из шага 5, а не публичный.

Затем войдите в панель с паролем из шага 4 и смените его в интерфейсе — он был лишь начальным. Ваш
узел появится в **Nodes** и выйдет в онлайн в течение одного интервала синхронизации.

Две вещи, на которые натыкаются сразу после этого:

- **Узел в онлайне, но клиенты не подключаются.** Это шаг 6 — брандмауэр. NixOS фильтрует `INPUT`, а
  интерфейса, которому панель выбрала порт, нет в вашем `udpPortRanges`.
- **На публичном адресе ничего не слушает.** Панель по умолчанию слушает `127.0.0.1`; см. замечание
  про `host` в шаге 5.

## Обновление

Панель никогда не запускает собственный апдейтер. Она трогает файл, а root-юнит решает, что значит
«обновиться» — `bootstrap.sh update` на голом железе, `compose pull && up` в Docker, а здесь
пересборка.

### Кнопка Update, включена по умолчанию

`selfUpdate.enable` по умолчанию `true`, с `flakeRef = "/etc/nixos#<hostname>"` и
`updateInputs = [ "swg-panel" ]`. Сниппет конфигурации, который печатает панель, называет свой
атрибут флейка `swg` и ставит `flakeRef = "/etc/nixos#swg"` под стать, так что на стоковой установке
кнопка работает без каких-либо дополнительных настроек. Меняйте это, только если ваш флейк лежит в
другом месте или его атрибут не совпадает с именем хоста:

```nix
services.swg-panel.selfUpdate = {
  flakeRef = "/etc/nixos#myhost";   # ваш флейк#атрибут; по умолчанию предполагается #<hostname>
  updateInputs = [ "swg-panel" ];   # обновляются перед пересборкой
};
```

`services.swg-node.selfUpdate` принимает те же три опции. На машине, где работает и то и другое, у
каждого свой триггер и свой юнит; они пересобирают одну и ту же машину, и каждый хранит свою
отметку, поэтому одна пересборка не провоцирует вторую.

⚠️ **`updateInputs` — это разница между обновлением и пустой операцией.** Пересборка собирает то,
что зафиксировано в вашем lock-файле, а это очень часто уже работающая версия — поэтому назовите
вход, из которого пришёл этот модуль, иначе кнопка отчитается об успехе и ничего не изменит. Это
касается только локального флейка: удалённый `flakeRef` каждый раз тянется заново, и указание
входов для него роняет сборку, а не тихо делает меньше, чем вы просили.

### Обновление вручную

```bash
sudo nix flake update swg-panel --flake /etc/nixos
sudo nixos-rebuild switch --flake /etc/nixos#myhost
```

Чтобы совсем убрать кнопку из этой цепочки, поставьте `selfUpdate.enable = false`. Диалог тогда
покажет точную команду `nixos-rebuild` и прямо скажет, что ничего не подключено, вместо того чтобы
позволить кнопке отчитаться об успехе и ничего не сделать. Узел ведёт себя так же и отказывается от
bootstrap-апдейтера — который на такой машине выглядит работающим, пишет в `/opt` и оставляет
установку, которой ваша конфигурация не видит, — сообщая, почему.

### ⚠️ В нативном варианте пересборка не перезапускает демон

Новая версия не вступает в силу, пока вы его не перезапустите. Это сделано намеренно: перезапуск
заново прогоняет bootstrap, который поднимает и опускает каждый интерфейс, и все подключённые
клиенты отваливаются до следующей сверки.

```bash
sudo systemctl restart swg-noded        # когда вы готовы к этому провалу связи
```

Поставьте `restartOnRebuild = true`, если предпочитаете, чтобы это происходило само.

### Когда пересборка падает, вы получаете причину

`nixos-rebuild` может упасть по причинам, никак не связанным с swg — из-за постороннего входа,
который не скачивается, из-за out-of-tree модуля ядра на новом ядре — и падает он *после* того, как
обновляемые службы уже перезапущены, так что внутри них этого никто не видит. Юнит записывает свой
вердикт и хвост вывода туда, где их читают панель и узел, поэтому интерфейс отличает «кнопка
сломана» от «пора двигать пин ядра». Когда флейка, которого ожидают значения по умолчанию, на месте
нет, пересборка падает с внятным сообщением — какой `flakeRef` поставить или как выключить и
запустить руками, — а не сырой ошибкой `nix`.

**Пересборка уступает дорогу, поэтому нажатие Update не может уронить машину.** `nixos-rebuild`
вычисляет систему целиком, и на небольшом входном сервере (2 CPU / ~2 ГБ) неограниченный запуск
насыщает оба ядра и загоняет память в reclaim — достаточно, чтобы sshd перестал отвечать, а панель
отдавать страницы, *пока идёт сборка*. Поэтому юнит обновления работает с пониженным приоритетом,
idle-IO и первым в очереди на отстрел по нехватке памяти: интерактивная работа всегда выигрывает, а
если память всё же кончится, ядро убьёт пересборку (она атомарна — работающая система не тронута) и
сообщит об этом, но никогда не панель и не демон. Так кнопка остаётся *безопасной* на машине любого
размера; чтобы она ещё и *срабатывала* на хосте меньше ~2 ГБ, дайте вычислению запас:

```nix
zramSwap.enable = true;      # или запись в swapDevices
```

В контейнерном варианте по-прежнему доступен `io.containers.autoupdate=registry` из podman, если вы
предпочитаете, чтобы за образом гонялась сама среда; этот модуль его не подключает.

## Перенос существующей установки на NixOS

Первое, что здесь скорее всего делают, — это не чистая установка, а перенос машины, которая уже
работает. На кону в этом переносе стоит **личность**: приватный ключ каждого интерфейса,
`wg-keys.dat` каждого экземпляра WDTT, хранилище паролей каждого csqtt и токен регистрации узла.
С каждым из них уже разговаривают клиенты, и перевыпуск любого выглядит ровно как удачный перенос —
ровно до того момента, когда клиенты перестанут подключаться.

Хорошая новость в том, что большая часть вообще никуда не переносится.

| откуда → куда | что переносится |
|---|---|
| голое железо → **native** | **ничего.** Нативный вариант намеренно сохраняет пути голого железа, и модуль их проверяет. |
| docker → **container** | **ничего.** Направьте модуль на каталоги, которые уже монтирует compose-стек. |
| голое железо → **container** | только пути, зависящие от модели запуска: WDTT, csqtt, их записи, запись turn. |
| docker → **native** | тот же набор в обратную сторону, плюс конфигурации интерфейсов. |

### ⚠️ Используйте прежний токен. Не выпускайте новый.

Узел опознаётся панелью по **токену**, и панель сопоставляет этот токен с записью, к которой
приписаны ваши пиры. Поэтому:

- **Правильно:** взять токен, который у машины уже есть — `adopt.sh` его находит
  (`/etc/swg-agent/config.json` на голом железе, `NODE_TOKEN` в docker-овском `.env`), а
  `--token-out FILE` выпишет его для вашего менеджера секретов. Если токен потерян — **Nodes → узел →
  Rotate token**, что выпускает новый токен для *той же самой* записи.
- **Неправильно:** «добавить узел» в панели и взять тот токен. Так создаётся *новая* запись. Машина
  поднимается как второй узел рядом с первым, и — поскольку у новой записи нет приписанных пиров —
  её следующая сверка **снимает все пиры с живого интерфейса**. Это измерено, а не предположено:
  именно это делает контрольный прогон в `probeM1-run.sh`, и именно поэтому `adopt.sh` читает токен
  за вас.

На **мастере** `localNode.name` должно совпадать с именем, под которым панель уже знает этот узел,
иначе сеятель регистрации допишет вторую запись рядом, а не обновит существующую. `adopt.sh`
печатает правильное имя — он находит его, сверяя токен с хэшем каждой записи, ровно так же, как это
делает панель.

### Порядок имеет значение

`nixos-rebuild` не может убрать юниты, установленные пакетным менеджером, а как только машина стала
декларативной, `/etc/systemd/system` доступен только на чтение — и в этот момент и `uninstall.sh`, и
`adopt.sh` **отказываются работать**, потому что `systemctl disable`, который там не срабатывает,
оставляет скрипт удаляющим файлы из-под работающих служб. Запускайте это **на машине с установкой,
пока она ещё императивная**.

#### Шаг 1 — отчёт (ничего не меняет)

```bash
sudo ./nix/adopt.sh --to native        # что здесь есть, что переносится, какую конфигурацию вставить
```

Добавьте `--token-out /etc/swg-secrets/node-token`, чтобы он выписал существующий токен за вас.

#### Шаг 2 — перенос, если маршруту он нужен

```bash
sudo ./nix/adopt.sh --to native --carry
```

Он копирует; оригиналы остаются на месте, поэтому прерывание ничего не теряет. На двух маршрутах,
где переносить нечего, это пустая операция.

#### Шаг 3 — отпустите старые юниты

```bash
sudo ./nix/adopt.sh --to native --release
```

Только юниты. Он останавливает каждую службу **и проверяет, что она действительно остановилась**,
прежде чем удалить её файл, и сохраняет состояние до последнего байта.

⚠️ **Не используйте для этого шага `uninstall.sh`.** Он отмечает узел ушедшим у панели
(`/api/node/goodbye`) и удаляет `/var/lib/swg-noded`, `/etc/swg-agent` и `/opt/swg-{wdtt,csqtt}` —
ровно ту личность, ради сохранения которой перенос и затевался.

#### Шаг 4 — опишите модуль и пересоберите

Оставьте `services.swg-node.interfaces` **незаданным**. Набор интерфейсов — это конфигурации,
которые уже лежат на диске; та опция лишь засевает узел, у которого их нет.

### Замечания по маршрутам

**голое железо → native.** Копировать нечего: `/etc/amnezia/amneziawg`, `/etc/wireguard`,
`/etc/swg-agent`, `/var/lib/swg-noded` и `/opt/{vk-turn-proxy,swg-wdtt,swg-csqtt}` уже там, где
модуль их ищет.

**docker → container.** Тоже копировать нечего — направьте модуль на каталоги, которые compose-стек
уже монтирует:

```nix
services.swg-node  = { stateDir = "/opt/swg-panel-docker/data/node"; confDir = "/opt/swg-panel-docker/data/node-confs"; };
services.swg-panel = { stateDir = "/opt/swg-panel-docker/data/lib"; configDir = "/opt/swg-panel-docker/data/etc";
                       statsDir = "/opt/swg-panel-docker/data/stats"; subTlsDir = "/opt/swg-panel-docker/data/sub-tls"; };
```

`--release` опускает compose-стек. Контейнеры `swg-turn-*` он намеренно не трогает: они не под
управлением compose, и узел подхватывает их обратно сразу же.

**Два перекрёстных маршрута.** `--carry` вызывает те же помощники, что и перевод docker↔голое
железо, поэтому карта путей в этом репозитории существует ровно в одном экземпляре. Он никогда не
перемещает — он копирует, и он громко жалуется, когда не может: тихий отказ здесь как раз и есть тот,
который выглядит успехом.

- **docker → native** дополнительно приносит конфигурации интерфейсов в `/etc/amnezia/amneziawg`
  (`stateDir` и `confDir` нативного узла нельзя перенести — модуль их проверяет). Одно **не**
  переезжает: turn-прокси. Узел в соглашении голого железа читает свой набор turn из **юнитов на
  диске**, а `adopt.sh` их не пишет, поэтому пересоздайте каждый прокси из панели после переноса —
  перенесённая запись хранит его listen/connect/форк, так что заново вводить ничего не придётся.
  Если на этой машине ещё стоит дистрибутив, поддерживаемый установщиками, `./convert.sh docker
  baremetal node` сделает тот же перенос *и* пересоберёт turn-юниты, после чего это станет маршрутом
  «копировать нечего» выше.
- **голое железо → container** переносит WDTT, csqtt и обе записи в `stateDir`, плюс запись turn (в
  этом варианте запись *и есть* конфигурация, и узел пересоздаёт каждый прокси как контейнер из
  неё). Конфигурации обычного WireGuard из `/etc/wireguard` тоже копируются в `confDir`:
  контейнерный узел никогда не монтирует этот каталог, поэтому оставленный там интерфейс тихо выпал
  бы из управляемого набора.

### Один дополнительный шаг для перенесённой нативной панели

Панель работает от `swgpanel:swg`, а NixOS выделяет этим учётным записям собственные id — поэтому
состояние, скопированное с другой машины, принадлежит uid, который здесь уже ничего не значит:

```bash
sudo chown -R swgpanel:swg /var/lib/swg-panel && sudo chown -R root:swg /etc/swg-panel
```

Пропустите это — и панель **откажется стартовать**, вместо того чтобы подняться на нечитаемом
реестре. Этот отказ намеренный и его стоит знать: панель, поднявшаяся с пустым реестром, сообщила бы
каждому узлу, что пиров нет, и узлы бы ей поверили.

Ваш существующий вход сохраняется. `environmentFile` по-прежнему обязателен, но его
`PANEL_PASSWORD` используется только для засева панели, у которой входа **нет** вовсе, — так что на
перенесённой он читается и игнорируется.

### Проверки, которые говорят, что всё получилось

- Панель показывает для этой машины **одну** запись, а не две, и она выходит в онлайн.
- Публичный ключ каждого интерфейса тот же, что и раньше (`awg show <iface> public-key`), а его пиры
  возвращаются после первой синхронизации.
- `sha256sum /opt/swg-wdtt/*/wg-keys.dat` не изменился по сравнению с тем, что было до переноса.

## Удаление

### Удаление узла

**1. Удалите узел в экране Nodes панели.** Оба установщика на выходе вызывают
`/api/node/goodbye`; удаление модуля из вашей конфигурации панели **не говорит ничего** —
`nixos-rebuild` останавливает юнит и уносит файлы, а со стороны панели это неотличимо от узла,
который просто замолчал. Он уходит в `dangling` и там и остаётся. Это тот же шаг, который вы сделали
бы для сгоревшей машины, и панель отображает это состояние верно: его пиры остаются приписанными,
пока вы его не удалите, — а это ровно то, чего вы хотите, пока вы узел *переносите*, а не выводите
из строя.

**2. Уберите модуль из конфигурации и пересоберите.**

```bash
sudo nano /etc/nixos/configuration.nix
```

Либо поставьте флаг, либо удалите весь блок `services.swg-node = { … };`:

```nix
services.swg-node.enable = false;
```

```bash
sudo nixos-rebuild switch --flake /etc/nixos#myhost
```

**Turn-прокси узла уходят вместе с ним.** В поколении их не описывает ничего — панель создаёт их во
время работы, соседними контейнерами в контейнерном варианте и юнитами `vk-turn-proxy-*` в нативном,
— поэтому удаление обязано остановить их явно, иначе они остаются работать, по-прежнему занимая свои
публичные UDP-порты на машине, которую вы только что вывели из эксплуатации. Делает это только
удаление: перезапуск или пересборка, которая всего лишь меняет узел, их не трогают. Чем они были,
остаётся вместе с остальным состоянием, поэтому повторное включение модуля возвращает их обратно.

**3. Удалите состояние руками, когда вы этого действительно хотите.** `stateDir`, `confDir` и ключи
интерфейсов пересборкой не удаляются — у `StateDirectory` нет семантики удаления, да и по умолчанию
это было бы здесь неверно: эти файлы и есть личность узла.

```bash
sudo rm -rf /var/lib/swg-noded /etc/amnezia/amneziawg /etc/wireguard /etc/swg-agent \
            /opt/swg-wdtt /opt/swg-csqtt /opt/vk-turn-proxy
```

Контейнерный узел может оставить после себя интерфейсы-пустышки с адресами — его
userspace-устройства, пережившие контейнер, на которых ничего не работает. Они безвредны и не мешают
повторной установке; уберите их через `ip link del <iface>`, если хотите чистую машину.

### Удаление панели

В `/etc/nixos/configuration.nix` либо поставьте флаг, либо удалите весь блок
`services.swg-panel = { … };`, затем пересоберите:

```nix
services.swg-panel.enable = false;
```

Пересборка уносит панель, swgSub, их юниты и их порты, а состояние оставляет. Удалите его, когда
действительно решите:

```bash
sudo rm -rf /var/lib/swg-panel /etc/swg-panel
```

⚠️ `/var/lib/swg-panel` — это **реестр**: все пиры, все записи узлов, вход и хранилище ключей
подписок. Другой копии нет. Сделайте резервную копию, прежде чем удалять.

### Удаление всего с машины

```bash
# 1. сначала удалите узел в панели (см. выше), затем пересоберите без обоих модулей в конфигурации:
sudo nixos-rebuild switch --flake /etc/nixos#myhost

# 2. состояние
sudo rm -rf /var/lib/swg-panel /var/lib/swg-noded /etc/swg-panel /etc/swg-agent \
            /etc/swg-secrets /etc/amnezia /etc/wireguard \
            /opt/swg-wdtt /opt/swg-csqtt /opt/vk-turn-proxy

# 3. оставшиеся туннельные устройства, если они есть
for i in $(ip -br link | awk '{print $1}' | grep -E '^(wg|awg|swg_|wdtt|csqtt)'); do
  sudo ip link del "$i"
done

# 4. в контейнерном варианте: образы, сети и собственные хвосты podman
sudo podman system reset -f
```

⚠️ **Именно `podman system reset`, а не `podman rmi -af`.** Удаление образов оставляет работать
DNS-помощник podman, который по-прежнему держит `10.88.0.1:53`, и следующий контейнер, которому
нужна сеть по умолчанию, не стартует с `aardvark-dns failed to start: … Address already in use` — на
машине, которую вы только что вычистили, то есть в последнем месте, где вы стали бы искать. `reset`
уносит и сети, и помощника.

⚠️ **`uninstall.sh` на декларативной машине отказывается работать, включая `--dry-run`**, и этот
отказ — правильный ответ: убрать юниты, которыми владеет `nixos-rebuild`, он не может, а убрать их
наполовину хуже, чем не начинать.

## Справочник

### csqtt в контейнерном варианте нужен `seccomp`

Датаплейн csqtt — это io_uring, и запасного пути у него нет, а профиль seccomp по умолчанию в обеих
средах запрещает `io_uring_setup` — поэтому сервер csqtt внутри контейнера узла умирает в тот же
миг, как стартует, со словами `create io_uring`. Это настройка контейнера, до которой панель никак
не дотягивается:

```nix
services.swg-node.seccomp = "unconfined";   # только если вы запускаете на этом узле серверы csqtt
```

По умолчанию так не сделано, потому что это выключает профиль для всего контейнера узла, а csqtt на
большинстве узлов не работает вовсе. WDTT и turn-прокси в этом не нуждаются. Панель подсказывает,
какую опцию поставить, когда видит такой отказ.

### Интерфейсов нет в вашем `configuration.nix`

Это сделано намеренно — они такое же состояние парка, как и пиры, а заставлять вас пересобирать
систему ради каждого интерфейса было бы другим продуктом, — но `nixos-rebuild` их не видит. Они
живут в `stateDir`/`confDir`, переживают откат системы, и `stateDir` обязан сохраняться, если у вас
impermanence.

### Access & TLS: только чтение, и откуда берётся адрес

Settings → **Access & TLS** — это весь механизм адреса и сертификата панели во всех остальных
случаях. Здесь это **представление только для чтения**: экран показывает опции, несущие адрес, на
котором панель действительно работает, а смену адреса, пути монтирования или сертификата панель
отклоняет на уровне API — и сохранение, и применение, — вместо того чтобы принять то, что следующая
пересборка отменит.

Значит, адрес держит модуль — и модуль его и записывает:

| опция | что она решает |
|---|---|
| `domain`, `basePath`, `port`, `useACMEHost` | URL, который объявляет панель, и терминирует ли она TLS сама |
| `publicUrl` | тот же URL дословно, когда выведенный выше — не он (прокси по обычному HTTP, необычный публичный порт) |
| `sub.domain`, `sub.basePath`, `sub.publicUrl` | база, из которой строится каждая ссылка подписки |

Всё это записывается в собственные настройки панели **при каждом старте**, поэтому адрес меняется
именно через `nixos-rebuild` — включая подтверждённую базовую отметку адреса, которая во всех
остальных случаях продвигается только через подтверждение в браузере, а здесь его выполнить негде.

**У операторской консоли может быть свой порт, и здесь это единственный способ её перенести.** В
остальных случаях оператор переключает это в Access & TLS и подтверждает в браузере; здесь экран
только для чтения, поэтому переключателем служит сама опция: задайте порт — консоль переедет туда,
оставьте 0 — дверь останется одна, как раньше.

```nix
services.swg-panel.consolePort = 8445;      # 0 = выключено, значение по умолчанию
services.swg-panel.consoleHost = "127.0.0.1";   # loopback: доступ через SSH-туннель, наружу ничего не торчит
```

Тогда `port` отвечает только на то, что спрашивают ноды, а на всё остальное возвращает **404** —
страницы консоли, операторский API, `/api/v1/*` и `/metrics` переезжают вместе с вами на порт консоли.
Для флота не меняется ничего: ноды ходят на тот же адрес, и он отвечает на те же маршруты.

Файрвол за вас никто не откроет. На loopback консоль доступна только с самой машины —
`ssh -L 8445:127.0.0.1:8445 <эта машина>`, затем `http://localhost:8445`, — и отдаётся по обычному
HTTP: на loopback подслушивать некому. Расширьте `consoleHost` — и она будет отдаваться с собственным
сертификатом панели, а правило файрвола писать вам.

**TLS вычтен, а не перенесён.** Образ панели несёт в себе acme.sh, и на голом железе им управляет
установщик; здесь не работает ни то ни другое. Сертификатами владеют `security.acme` и ваш обратный
прокси — ровно так, как это делает любой сопоставимый модуль в nixpkgs.

Привилегированный помощник, которым панель пользуется для этого в других местах (`swg-netctl`), **не
устанавливается ни в одном из вариантов** — и не нужен: с этой защитой ни один запрос, который панель
может сделать, до его очереди не доходит. Измерено в обоих вариантах, против обычной панели, которая
в очередь ставит.

### Как swgSub отделён от панели

Это единственный процесс здесь, который намеренно доступен из интернета, поэтому он отделён сразу по
четырём осям:

- **другой пользователь** (`swgsub`, группа `swg`) — никогда не пользователь панели;
- **файловая система только на чтение** (`ProtectSystem=strict` и ни одного `ReadWritePaths`);
- **собственный материал TLS** в собственном каталоге — отдать приватный ключ панели этому процессу
  значило бы позволить его компрометации выдавать себя за панель;
- и **маска на уровне ядра** поверх шести путей, которые он не должен открывать никогда: хэш входа,
  каталог TLS панели, хранилище ключей подписок, эскроу, секреты вебхуков/API и любые сохранённые
  клиентские конфигурации. Именно маска, а не просто отсутствие прав на чтение, — чтобы ошибка в
  этом процессе не дотянулась до них, даже если бы права на файлах оказались неверны.

### Где заканчивается поддержка

**Нативным датапатом владеет nixpkgs.** `linuxPackages.amneziawg` — это out-of-tree модуль ядра,
который поддерживают там, а не здесь; когда он перестаёт собираться на новом ядре, это вопрос к
nixpkgs, и мы поможем, но владеем им не мы. Контейнерный вариант мы поддерживаем целиком, потому что
в нём ничто не зависит от дерева ядра хоста.

Эта граница терпима только потому, что восстановление — две строки и не стоит вам продукта:

```nix
services.swg-node.kernelModule = false;   # откатиться на userspace-датапат
```

`awg-quick` сначала пробует ядерное устройство и использует `amneziawg-go`, когда его нет, поэтому
больше ничего не меняется — те же интерфейсы, те же пиры, те же файлы конфигурации, меньше
пропускной способности. Включите обратно, когда модуль снова соберётся.

Всё это ещё и снабжено приборами, а не таинственно: упавшая пересборка записывает свою причину и
хвост вывода туда, где их читают панель и узел, поэтому диалог обновления говорит *пора двигать пин
ядра*, а не *кнопка сломана*. И собственный CI этого репозитория еженедельно прогоняет плавающий
nixpkgs против обоих наборов виртуалок ровно ради этого — раннее предупреждение должно доходить до
нас раньше, чем до вас.

### Смена `delivery` на работающем узле

Поменять `delivery` и пересобрать — это не миграция, и такой она не поддерживается: два варианта
намеренно держат состояние в разных местах, поэтому вместе с ней меняется и то, что работающий узел
вообще видит. Измерено на живом мастере, native → container → native:

- **Интерфейсы обычного WireGuard исчезают.** Их конфигурации лежат в `/etc/wireguard`, который
  контейнер не монтирует (ему достаётся только `confDir`, а установка контейнерного варианта пишет
  туда *все* конфигурации, и `wg`, и `awg`). Сам интерфейс продолжает работать — панель показывает
  его как **отсутствующий с предложением восстановить**, и он возвращается, когда вы переключитесь
  обратно.
- **turn / WDTT / csqtt уходят вместе с вариантом.** Форк-серверы нативного варианта — это юниты
  хоста с состоянием в `/opt`; у контейнерного это управляемые подпроцессы в смонтированном каталоге
  состояния. Ни один не видит чужого, поэтому панель показывает их отсутствующими на том варианте,
  который их не ставил. Копии на хосте не тронуты — личности и хранилища паролей переживают путь
  туда и обратно.
- **Управление turn включается вручную только в контейнерном варианте.** Нативный узел управляет
  turn-прокси безусловно, поэтому переключение выключает это, если вы не попросили обратного, и
  карточки turn в панели становятся только для чтения со строкой, объясняющей почему.

Если вам нужен другой вариант, лучше пересоздайте интерфейсы узла на нём, чем переключайте на месте.
Если всё же переключаете — ждите, что панель проведёт вас по восстановлениям: ни один ключ ни в
одном из случаев выше не теряется.

Нативный вариант намеренно сохраняет **пути голого железа** (`/var/lib/swg-noded`,
`/etc/amnezia/amneziawg`) — именно поэтому
[перенос существующего узла с голого железа](#перенос-существующей-установки-на-nixos) не переносит
вообще никаких данных.

### Жизнь с декларативной машиной

Четыре вещи, на которых этот репозиторий обжёгся, и ни одна из них не очевидна с одной стороны.

**`networking.nftables.flushRuleset` — поставьте `false`, если вы пользуетесь nftables.** Он сам
переключается в `true`, стоит вам задать `nftables.ruleset` или `rulesetFile` (а также при
`stateVersion` ниже 23.11), и тогда каждая перезагрузка правил выдаёт `flush ruleset`, который
уносит вместе с собой и наши таблицы. Маршрутизация и блокировки чинят себя сами на следующей
сверке, поэтому симптом — минута трафика, идущего не туда, после посторонней пересборки; самый
трудный вид жалобы.

```nix
networking.nftables.flushRuleset = false;
```

Учтите и то, что `networking.nftables.enable` заносит `ip_tables` в чёрный список, а это убивает
iptables-**legacy**. `iptables-nft` это не затрагивает, и пользуемся мы именно им.

**Рискованным датапат делает закрепление `boot.kernelPackages`**, а не NixOS. На ядре по умолчанию
из канала модуль AmneziaWG приходит уже собранным с cache.nixos.org; закрепите ядро выше того, что
собрала Hydra, — и вы просите out-of-tree модуль собраться против ядра, на котором его никто не
пробовал, а поскольку он является зависимостью сборки замыкания вашей системы, его неудача роняет
весь `nixos-rebuild`. Восстановление в две строки — в разделе
[Где заканчивается поддержка](#где-заканчивается-поддержка) выше.

**Impermanence: `/var/lib/swg-noded/` обязан сохраняться.** Узел, зарегистрированный по токену,
переживает стирание в духе «erase your darlings», потому что токен приходит заново из ваших
секретов. **Самостоятельно сгенерированные личности — нет**: приватный ключ каждого интерфейса
генерируется на узле и живёт там же. Сотрите этот каталог — и публичный ключ в `[Peer]` у каждого
клиента перестанет совпадать: панель по-прежнему показывает узел, интерфейс по-прежнему поднимается,
и ничего не устанавливает соединение. Скачанные бинарники форков живут там же и намеренно не входят
в замыкание, так что откат их тоже не вернёт.

**`nixos-rebuild --rollback` откатывает код, а не состояние.** Пиры, интерфейсы и списки
маршрутизации — это состояние парка, которым владеет панель: откат возвращает прежние программы, и
они читают сегодняшнее состояние. Это то поведение, которое вам и нужно, но знать о нём стоит до
того, как вы за ним потянетесь.

### Что содержит пакет

Одна деривация, потому что репозиторий — одно целое: `VERSION` является единственным источником
истины, который штампуется в каждый компонент, поэтому разделение поставило бы расхождение версий в
одну пересборку от вас.

| путь | что |
|---|---|
| `libexec/swg-panel/` | `swg-panel-server` + SPA (`js/`, `vendor/`, `index.html`, …) + `VERSION` |
| `libexec/swg-sub/` | `swg-sub` + его статика + `VERSION` — отдельный юнит, пользователь и каталог TLS |
| `libexec/swg-noded/` | `swg-noded`, `swg-sni`, `VERSION` |
| `libexec/swg-agent/` | `swg-agent` |
| `libexec/swg-node/` | `node-entrypoint.sh` — bootstrap узла, общий с образами контейнеров |
| `bin/` | `swg-netctl`, `swg-passwd` и обёртки для пяти программ выше |

Две программы ищут файлы **относительно себя** — `swg-noded` ищет рядом с собой `VERSION` и
`swg-sni`, а панель и `swg-sub` откатываются к `VERSION` рядом с собой, — поэтому каждая программа
поставляется в каталоге со своими данными, повторяя то, что установщики пишут в `/opt`. Записи в
`bin/` **exec**-ают эти пути, а не ссылаются на них символически: для симлинка на скрипт ядро
передаёт интерпретатору путь *симлинка*, и оба поиска промахнулись бы. Это измерено, а не
предположено — панель, запущенная через симлинк, сообщает пустую версию.

`#!/usr/bin/env python3` у каждой программы во время сборки переписывается на интерпретатор из
store, поэтому узел не зависит от наличия `python3` в системном профиле. (`node-entrypoint.sh`
по-прежнему вызывает `python3` из `PATH`, чтобы вычислить подсети интерфейсов, так что модуль его
всё равно предоставляет.)

### Чем Nix *не* управляет

Панель поддерживает в свежем виде многое, и большая часть этого — **данные, а не код**: бинарники
форков turn-прокси, списки маршрутизации и блокировок, GeoIP, каталог, отпечатки TLS. Всё это
продолжает работать нетронутым. Управляемый store набор — это четыре артефакта: три программы на
Python и SPA.

⚠️ **Скачанных бинарников форков нет в замыкании.** Они живут в каталоге состояния узла, и это
сделано намеренно (это сторонние артефакты из динамического каталога, не наше дело их закреплять),
но означает, что `nixos-rebuild --rollback` их не восстановит. `/var/lib/swg-noded/` обязан
сохраняться.

### Что поддерживается

| | |
|---|---|
| `nix/package.nix`, `flake.nix`, `default.nix` | пакет, оверлей, `checks` |
| `services.swg-node`, `delivery = "container"` | поставляемый образ под управлением `virtualisation.oci-containers` |
| `services.swg-node`, `delivery = "native"` | наши программы из store, ядерный датапат, юниты хоста |
| `udpPortRanges` | столкновение «порт во время работы ↔ брандмауэр во время сборки»: открыт и отражён в отчёте |
| `services.swg-panel`, оба варианта | плоскость управления; swgSub едет вместе в обоих |
| swgSub, оба варианта | свой пользователь, свой каталог TLS и маска ядра на шесть путей |
| защита Access & TLS | экран только для чтения; адрес записывает модуль, в обоих вариантах |
| самообновление | кнопка Update как `nixos-rebuild switch --flake`, включена по умолчанию, с пониженным приоритетом, чтобы не заморить машину, и с причиной отказа |
| роль мастера | панель + узел рядом, зарегистрированные из одного общего файла с токеном |
| перенос | перенос существующей установки с голого железа или docker на любой из вариантов, с сохранением личности |
| тесты в виртуалках + CI | `checks.x86_64-linux.{fleet-native,container-arm}`, еженедельно против нашего пина и против канала |
| установщики здесь отказываются | `bootstrap.sh` и пять установщиков распознают декларативную машину и останавливаются |

### Намерение по upstream

Пространства опций `services.swg-panel` и `services.swg-node` **закреплены за этим репозиторием**.
Модуль поддерживается здесь, на том же коммите, что и код, который он запускает, а не в отдельном
репозитории `swg-panel-nix` — так делает любой сопоставимый проект, поставляющий собственный модуль
NixOS, и по той же причине. Если модуль для swg-panel когда-нибудь предложат в nixpkgs, это должен
быть этот же модуль, перенесённый туда: два модуля, владеющие одним пространством имён, ломаются у
всякого, кто импортирует оба.

Против флейка гоняются два набора виртуалок — панель и настоящий нативный узел, сходящиеся на
ядерном датапате, и хостовая половина контейнерного варианта. Еженедельный workflow собирает оба
**дважды**: один раз против зафиксированного `flake.lock`, что защищает наши собственные изменения,
и один раз с входом nixpkgs, отпущенным на канал, — это и есть раннее предупреждение о границе
поддержки выше, и ему позволено падать, не роняя весь прогон. `.github/workflows/nix.yml`;
намеренно в стороне от пути сборки образов.
